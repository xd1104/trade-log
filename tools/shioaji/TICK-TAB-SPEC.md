## 0. 這一頁的目的（先讀，會影響每個取捨）

即時分頁回答「**今天走到哪**」。這一頁回答「**那 45 分鐘裡，每一秒發生什麼**」。

真正的區隔不是「今天 vs 那 45 分鐘」——即時分頁本來就看得到那 45 分鐘。
**區隔是「多細」**：他那一單 290 秒，在即時的 5 分 K 上是 **1 根**；
30 秒桶約 **10 根**；1 秒桶 **290 根**。
而 K 棒比折線多給的東西是「這一段摸到多高多低」，那正是 **±100 觸價規則**在意的
（觸價是看有沒有摸到，不是看收在哪）。所以預設圖種是**秒級 K 棒**。

### ⛔ 紅線（不可違反，跟回顧分頁同一套）

- UI 上不得出現任何**預測／勝率預估／期望值／買賣建議／訊號強度**，
  也不准出現「相似歷史情境的後續走勢」這類暗示。文案禁詞見 §12 驗收 5。
- **只畫已經發生的客觀事實**：成交價、買賣價、成交量、他自己那一單、缺口。
- **±100 線只有在「那天真的有這一單」時才畫**，畫的是那一單的停利停損位置。
  ⛔ 沒有交易的日子**不准**畫「如果現在進場的話 ±100 會在哪」——那是建議。
- 台股慣例 `--up` 紅＝漲/賺、`--down` 綠＝跌/賠。
  **效能數字、筆數、桶寬、缺口筆數這些非損益資訊一律不准用紅綠**（用 `--dim`／`--gold`）。
- 這一頁**一行都不碰下單路徑**，也不碰 `on_tick`（見 §7.6）。

### 1.1 分頁

頂列 segmented 從兩顆變三顆，沿用 `.seg`：

```

```

- 分頁名用「**細節**」（兩個字，跟左右等寬；`data-tab="tick"`）。

## 2. 圖種：C 秒級 K 棒（預設）＋ A／B 可切

Benson 2026-09-07 拍板：**預設 C**，A、B 做成可切的鈕。

| 鍵 | 鈕 | 畫什麼 | 預設疊圖 |
|---|---|---|---|
| `C` | **秒K**（預設 on） | 每 N 秒收成一根 K 棒（開高低收），紅漲綠跌跟面板同一套 | 成交量 **開** |
| `A` | 折線 | 成交價逐筆連起來（經像素分桶） | 成交量 關 |
| `B` | 折線+價帶 | A 再加「買價～賣價」的半透明帶 | 成交量 關 |

- 三顆共用同一個視窗（`TK.view`）、同一套疊圖狀態，**切圖種不重設縮放**。
- **A/B 的成交量預設關**：折線與量柱是兩種語言，疊在一起在 45 分鐘全景下會吵；
  要開得起來，但別預設。
- **B 的價帶只有 1~5 點寬**，全景幾乎看不出來 —— 這是事實不是 bug，
  在 `.tk-read` 讀值列把當下的買賣價差用數字寫出來補足（「買/賣 差 2」）。

### 2.1 秒 K 的桶寬

```
BARSEC = [1, 2, 5, 10, 15, 30, 60]
自動 = 讓畫面上大約 150 根 ⇒ want = 視窗秒數 / 150，取 BARSEC 中第一個 ≥ want 的值
```

- 45 分鐘全景 ⇒ 自動落在 **30 秒**（90 根）；放大到 5 分鐘 ⇒ **2 秒**；
  放大到 1 分鐘 ⇒ **1 秒**（60 根，每根 16px 寬，紅綠看得清楚）。
- 手動鈕給 `自動 / 1 / 5 / 30`（10、15、60 由自動涵蓋，四顆就夠，別做七顆）。
- **1 秒是這張圖的原子單位**，往下不再細分（原因見 §7.2）。
- 桶的邊界一律 `floor(時間 / 桶寬) * 桶寬`（對齊整秒的絕對格線），
  **不可以用「從第一筆開始每 N 秒」**——那樣換視窗時每根 K 棒都會重新切一次、
  形狀跟著滑動，看起來像資料在變。
- 聚合結果要快取，key = `日期|桶寬`；資料或桶寬沒變就不重算。

### 2.2 K 棒畫法

```
影線：x 取整數 +0.5，1px，顏色 = 該根紅綠
實體：寬 = min(14, 一根的像素寬 × 0.66)，最小 1px；高度最小 1.2px（十字線不可以消失）
紅綠：收 ≥ 開 ⇒ --up(#EE5A54)；收 < 開 ⇒ --down(#34B37E)
```

## 3. 時間軸

### 3.1 預設固定 08:45:00 ~ 09:30:00（PM 拍板）

- 一打開就是完整的 45 分鐘框，**不管那天錄到多少**。
  這樣每一天的圖都在同一個框裡，翻頁時才比得起來。
- **缺的那段畫斜線 ＋ 一句人話**：
  ```
  斜線：45° hatch，stroke rgba(141,149,163,.18)，間距 7px
  文案：「這段沒有錄到（不是沒行情）」
  ```
  ⛔ **這句話一定要說出「不是沒行情」**。空白的那一段長得跟「行情沒動」一模一樣，
  他早上是照圖判斷的，看不出差別會直接誤讀。
- **未到的那段**（看今天、現在才 09:05）：同樣的斜線但更淡（`.10`），文案「還沒到」。
  ⚠️ 兩者的文案必須不同：一個是「我們漏了」，一個是「時間還沒走到」。
- 保留一顆切換鈕「**只畫有資料的那段**」（`.tk-tools` 的 chip，預設 off）：
  放大看細節時固定框會浪費一半畫面。切過去時 `TK.view` 重設為資料的頭尾。

### 3.2 刻度

- ⛔ **秒級時間軸一律印完整 `HH:MM:SS`**。只印 `MM:SS` 的話，放大到 12 秒時
  「14:05」會被讀成下午兩點零五（demo 實測踩到）。
- 刻度密度：`PW / 110` 個標籤上限；間隔從
  `[1,2,5,10,15,30,60,120,300,600,900]` 秒挑第一個裝得下的。
- **09:30 收手線**：一條 `--gold` 虛線 ＋ 下緣標籤「09:30 收手」。
  標籤放**下緣**不放上緣（上緣要留給 §4.3 的邊緣籤，兩張會互相壓）。
- 08:45~09:30 整段鋪 `--gold` 的 `.05` 底色（沿用面板「下單時段」的表達）。

## 4. 價格軸

### 4.1 `niceStep()` ＋ 遲滯（**必抄，不是優化**）

即時分頁 2026-09-02 修過一次「軸一直重算、整張圖跳」，
**這張圖比 5 分 K 嚴重得多**：資料密 40 倍、拖曳縮放是主要操作、
最後一根還在長。沒有這兩層一定會重演，而且更難看。

```js
function niceStep(raw){                       // 1/2/2.5/5/10 × 10^n
  if(!(raw>0)) return 1;
  const e=Math.pow(10,Math.floor(Math.log10(raw))), r=raw/e;
  return (r<=1?1:r<=2?2:r<=2.5?2.5:r<=5?5:10)*e;
}
```

**遲滯規則**（跟即時分頁同一套，key 不同）：

- 遲滯 key = `日期 | 圖種 | 視窗起 | 視窗迄 | 桶寬`。key 一變就重新貼合
  （縮放／平移／換日／換圖種要能立刻對上，不然會出現「軸黏在上一個視窗」的鬼影）。
- key 沒變時：**舊軸還包得住新資料，而且新資料的高度沒有縮到舊軸的 55% 以下，就沿用舊軸**。
- 刻度線從 `lo` 往上取第一個 step 整數倍開始畫。
- 上下各留 6% 的 padding 再套 `niceStep`。

> ⚠️ **實作後更正（2026-09-07，lab-dev 實測 ＋ lab-qa 查證）**：真正在守這張圖的是
> **`niceStep()` 不是遲滯**。時間軸預設固定 08:45~09:30、資料只增不減 ⇒ 新範圍永遠
> 不會被舊軸包住 ⇒ 遲滯的 early-return **結構上進不去**（拿掉之後整條軸的變化序列
> 逐字相同）；拿掉 `niceStep` 的貼齊才會從 3 次變 16 次。
> 而且**以現在的 key（含視窗起訖），做滑動視窗也不會承重** —— 跟隨右緣時
> `TK.view.t0/t1` 每一格都變、key 每一格都變，滑動視窗正好是遲滯**最沒用**的場景。
> 要做滑動視窗**得先改 key**。所以 §12-7 的負控組**不可以**寫成「拿掉遲滯」，
> 見那一節的更正。

### 4.1b ⚠️ 量這一節的時候最容易量錯的地方（寫在這裡免得下一個人重踩）

**測不分桶的負控組時，測試資料必須用次秒解析度。**
若用整數秒，40,000 個點只會落在 **2,700 個相異 x** 上 ⇒「不分桶」那條折線退化成
一堆零長度線段，被瀏覽器便宜地帶過 ⇒ 負控組量到 **27 ms、而且跑三次差兩倍**。
下一個人會據此以為「不分桶其實也還好」而**把分桶拿掉**。

**量錯了所以做錯決定，比一條測試紅掉嚴重**（測試紅了會有人來看，量錯了沒有人會來看）。
同一族的兩個尺自證：① 先跑一次「空 rAF 迴圈」，每格不接近 16.7 ms 就代表 headless
根本沒在合成，上面所有 fps 數字都是骰子；② 事件處理耗時（真滑鼠拖曳量到的）與
每格畫面耗時（等一個 rAF）是**兩種時間**，只量前者會系統性低估。

### 4.2 ±100 線不撐大價格軸（PM 拍板）

- ±100 停利停損線畫得到就畫（`--up` / `--down` 的虛線 ＋ 右軸價籤）。
- **畫不到就不畫，改在對應那一側的邊緣掛一張籤**：
  ```
  ↑ 停利 +100 在畫面上方 38 點處
  ↓ 停損 −100 在畫面下方 62 點處
  ```
- ⛔ **不准把 ±100 納進價格軸的 hi/lo 計算**。那 45 分鐘的真實振幅常常只有 30~60 點，
  硬把 ±200 的範圍塞進來會把真正的波動壓成一條直線 —— 那正是這一頁唯一要看的東西。

### 4.3 交易標記同理

- 進出場價**只有在「那一單真的落在目前視窗的時間範圍裡」時才納入價格軸**。
  不在畫面裡就整組不畫，改用邊緣籤講清楚它在哪一邊、差多少。
- ⛔ **不要把標記黏在畫面邊緣假裝畫得出來** —— 看的人會以為那一單就發生在畫面邊上。
- ⚠️ 真實單的 `exit` 可能是 `null`（問不到成交價）。
  `Math.min(lo, t.entry, t.exit)` 會把 `null` 當 **0**，價格軸整個掉到 0
  （2026-09-02 踩過，`tabs-visual.mjs` 在守）。**餵進算式前一律先 `!= null` 過濾。**

### 5.1 成交量（**做，疊在下緣**）

`on_tick` 已經在錄單筆量（`{"k":"t",...,"v":3}`），所以做得出來。決定與理由：

- **疊在圖的下緣**，佔繪圖區高度的 **22%**，不開獨立副圖。
  理由：即時分頁的 K 線圖就是這樣畫的（量柱在同一張圖的下段），
  **沿用既有視覺語言**；而且獨立副圖會把本來就只有 380px 高（設計座標）的圖再切一刀。
  ⚠️ 22% 是**比例**：2026-09-08 圖縮 19% 之後量柱區跟著從 130.5 縮到 103.8px
  （1500px 視窗實測），仍與即時分頁那張的 115px 同一個量級。⛔ 要再縮圖的話縮價格區，
  **不准改這個 22%**（守衛 `tick-tab.mjs` ⑪ 斷言比例與量柱畫得出高低差）。
- 量 = **桶內加總**（不是平均、不是筆數）。桶寬跟著秒K 的桶寬走；
  折線模式下用「像素欄」當桶（一欄一根）。
- 量柱的紅綠 = **該桶的漲跌**（收 ≥ 開 為紅），跟即時分頁一致。
  ⛔ **絕對不可以標成「買量／賣量」或「內外盤」** —— 逐筆紀錄裡沒有這個旗標，
  那會是編出來的資訊。
- 量軸**不畫刻度數字**，只在量區右上角標一個「最大 N 口」。
  秒級成交量的絕對值沒有解讀價值，要看的是相對高低。
- 量區與價格區之間畫一條 `--line-soft` 的細線分隔，量區不與 K 棒重疊。
- ⛔⛔ **取樣日沒有量**（2026-09-07 加）。`tick_recorder.py` 只記價格與買賣價；
  `vol_ratio` 是「**累積**量 ÷ 歷史中位」，**不是單筆量**。
  所以取樣日這顆疊圖一律 **disabled ＋ 寫出原因**（跟 §5.2 同一套處理），
  而且「開不開這顆，畫出來要一模一樣」（探針在守）。
  ⛔ **絕對不可以拿 `vol_ratio` 之類的東西湊一根看起來像的量柱。**

### 5.2 加權指數（**實際上做不了，這一顆是 disabled 的**）

⚠️ 這一節寫的是 demo 期的設計，但 **`tick_logs` 的逐筆檔根本沒有指數這一欄** ⇒
上線時這顆一律停用並寫出原因。⛔ 不可以拿別的來源硬湊一條「看起來像」的線。

⚠️ 2026-09-07 補：**取樣檔其實有 `idx`**（`tick_recorder.py` 有記），

原本的設計（留著備查）：

- 第二條線，**用自己的 min/max 映射到同一個框**，右側**不另外畫第二條軸**
  （兩條軸會讓人以為兩條線的價差有意義）。

### 5.3 ⛔ 基差絕對不做逐筆線（PM 拍板）

demo 期間量到基差在逐筆尺度上跳動 51~200 點。
那**不是行情**，是取樣落差：期貨成交價 0.4~0.5 秒跳一次、加權指數 6.2 秒才動一次

## 6. 翻頁（可以翻過去的日子）

### 6.1 沿用即時分頁那排 `◀ 日期 ▶ 今天`，但把月曆換成清單

**沿用的部分（照抄 `pagerHTML()` 的結構與 CSS）：**

```
r1:  ◀   📅 09-08 一 ▾   ▶      ● 即時 ／ [今天]
r2:  逐筆 128,431 筆 · 08:45:02~09:29:59 · ← → 換日
```

- 位置一樣（圖卡標頭右側）、手勢一樣（◀▶、鍵盤 ←→、Home 回今天）、
  日期鈕點開一個 popover。**同一張圖卡上的同一個動作就該長同一個樣子**；
  在第三個分頁上另發明一套導航，是「同一件事有兩種語言」的典型病。
- **`.tk-pager` 是獨立節點，不可以跟會每秒重繪的東西寫在同一串 innerHTML**
  （即時分頁踩過：`#cupd` 那個坑 —— 報價每秒跳一次，翻頁列跟著被重建，
  ◀ 會在滑鼠底下被換掉）。

**改掉的部分：日期鈕點開的是「有錄到的日子」清單，不是迷你月曆。**

理由：即時分頁的月曆背後有 70 個交易日、每天都有漲跌與震幅可以畫；
這裡的母體是「有逐筆檔的日子」——**上線第一週只有 0~3 天**，
一個 95% 格子都是灰的月曆傳達的是「壞了」，不是「沒有資料」。
清單則可以在每一列寫出這一頁真正在意的東西：

```
09-08 一    128,431 筆   08:45:02~09:29:59
09-05 五     94,102 筆   09:03:00~09:29:58   ⚠ 缺 08:45~09:03
────────────────────────────────────────
更早以前沒有逐筆紀錄（2026-09-08 才開始錄）
```

⚠️ CLAUDE.md 記著「即時分頁的清單案被捨棄」——那是因為**那些資訊回顧分頁已經有了**。
這裡的清單放的是缺口與涵蓋時段，**全站沒有第二個地方看得到**，不是同一件事。

### 6.2 有哪幾天有資料：⛔ 不可以只看檔名

`tick_logs/` 底下同時住著兩種 schema：

| 檔名 | 誰寫的 | schema |
|---|---|---|
| `YYYY-MM-DD.jsonl` | `tick_writer.py`（面板 `on_tick`） | `{"k":"t"/"b"/"x"/"h", ...}` **逐筆** |
| `YYYY-MM-DD-polled.jsonl` | `tick_recorder.py`（每 0.1 秒讀 `/api/state`） | `{"t":...,"price":...,"mom5":...}` **取樣**，完全不同 |

**⛔ 磁碟上現在就有一個反例。** 寫這份規格時實際掃過
`tools/shioaji/tick_logs/2026-09-07.jsonl`：**2,972 列，每一列都是輪詢 schema**
（`t/ms/clock/price/bid/ask/mom5/idx/basis`…，**一個 `k` 欄位都沒有**）。
那是 `tick_recorder.py` 加上 `-polled` 後綴**之前**留下來的檔。
所以「列 `*.jsonl` 再排除 `*-polled.jsonl`」這個做法，**上線第一天就會把它當成逐筆檔**，
畫出一張空圖或直接爆掉。

**判定規則（兩道，都要）：**

1. 檔名必須完全符合下面**兩個**正則其中之一，各自對應一種 schema：
   - `^\d{4}-\d{2}-\d{2}\.jsonl$` ⇒ 逐筆（`kind:"tick"`）
   - `^\d{4}-\d{2}-\d{2}-polled\.jsonl$` ⇒ 取樣（`kind:"polled"`），**2026-09-07 加**
2. **嗅探內容，而且 kind 要跟檔名一致**：讀開頭最多 8 KB，逐列 `json.loads`（壞列跳過）。
   - 逐筆檔名 ⇒ **必須至少有一列帶 `"k"` 欄位**。
     第一列是 `{"k":"h"}` 時記下 `v`（格式版本）備用。
   - 取樣檔名 ⇒ 必須至少有一列**帶 `price` ＋ 讀得懂的 `t`、而且不帶 `k`**。
   - 嗅不到 ⇒ **不列進日期清單**，並在 server console 印一行
     `⚠️ [tick] 跳過 2026-09-07.jsonl：內容不是逐筆格式（…）`。
     ⛔ **不要靜靜跳過**（會變成「我明明有錄怎麼看不到」的無解客訴），
     也 ⛔ **不准自作主張改名或刪除** —— 那是 Benson 的資料。
3. 檔案存在但只有檔頭、一列資料都沒有 ⇒ 列出來但 `empty:true`，
   UI 上灰掉不可選（跟「休市日要選不到」同一個處置）。

**⛔⛔ 2026-09-07 的修訂只放寬「檔名」，沒有放寬 schema 檢查。**
上面那個反例（逐筆檔名 ＋ 取樣內容）**必須繼續被擋掉並列進 `skipped`** ——
那是這整條規則的原始目的。兩件事不要混：
「多接受一種檔名」≠「同一種檔名多接受一種內容」。

**為什麼改**：他 2026-09-07 早上的行情**只有取樣檔**（面板 12:16 才重啟、
逐筆落地那時才生效），而這一頁完全讀不到它 —— 那份是真的行情、而且含他當天那一單。
「不要讓取樣冒充逐筆」的正解是**在畫面上標示清楚**，不是整個不給看。

**同一天兩種檔都有的時候：逐筆優先**，另一種標 `alt:true`（清單寫「＋取樣檔」，
長說明放 `title` —— 長字串會把 `.meta` 擠到換行，那一列就比別列高一截）。
理由：逐筆是取樣的上位集合（有每一筆、有成交量），而且是面板自己寫的、
不會因為外掛工具中途被關掉而少一段。現在不會發生，但 `tick_recorder.py` 還在。

**⛔⛔ 「有沒有那種檔」問的是嗅探，不是 `path.exists()`**（2026-09-07 lab-qa 退件 M1）。
`/api/tick/day` 那一半原本按**檔案存不存在**挑（`_tick_load()` 拿不到才退到取樣），
於是一個「逐筆檔名 ＋ 取樣內容」的檔 —— **上面那個磁碟上真的存在的反例** ——
被 `/api/tick/days` 的嗅探擋掉之後，`/api/tick/day` **照樣端得出來**，
而且把同一天真正的取樣檔整份蓋掉：清單寫「取樣」、點進去圖上寫「逐筆」、沒有金籤、
成交量那顆變回可以按、空狀態寫「這天只有檔頭，一筆成交都沒有錄到」——
**一句假話**（那天有 1,091 列）。
⇒ `_tick_load()` / `_tick_load_polled()` **自己先嗅探、嗅不過就回 None**，
兩個端點才會用同一把尺。**不變式：`/api/tick/day` 的 `kind`
必須等於 `/api/tick/days` 清單上那天的 `kind`。**

**被跳過的檔要一直看得到**（不是只在「一個紀錄都沒有」的空狀態）：
日期清單底下常駐一行「⚠ 有 N 個檔被跳過（日期）：檔名對、但內容跟檔名不是同一種格式」。
只寫在空狀態的話，只要有任何一天有資料，「我明明有錄怎麼看不到」就完全無解。

**取樣日的畫面差異（⛔ 三處都要，不是只放在資料裡）：**

| 位置 | 逐筆 | 取樣 |
|---|---|---|
| 副標 | `08:45~09:30 · 逐秒` | `08:45~09:30 · 取樣 約 0.46 秒一筆`＋`取樣資料，不是逐筆` |
| 圖上 | 無 | 繪圖區**左下角**一張金色籤：`取樣 · 約 0.46 秒一筆 · 不是逐筆 · 高低＝取樣點的極值` |
| 日期清單 | 每列一顆`逐筆`標 | 每列一顆`取樣`標（⛔ **兩種都標** —— 只標一種的話，沒有標記等於「不知道」） |
| 翻頁列 | `逐筆 N 筆` | `取樣 N 筆` |
| 頁尾 | `tick_logs/DATE.jsonl` | `tick_logs/DATE-polled.jsonl` ＋ 一句怎麼錄的 |
| 成交量疊圖 | 可用 | **disabled ＋ 寫出原因**（跟「加權」同一套）；⛔ 絕不可以拿 `vol_ratio` 湊假量柱 |
| 缺口文案 | `這段沒有錄到（不是沒行情）` | `這段沒有取樣到（沒錄到，或報價一直沒變）` |
| 買賣價帶 | 有 | **有**（`bid`/`ask` 照樣記得到 ⇒「折線＋價帶」對取樣日照樣能用） |

⚠️ 圖上那張籤放**左下角**是因為左上角是「我那一單在左/右邊」的邊緣籤、
右側是「±100 在畫面外」與「09:30 收手」—— 三張擠在同一行會互相壓掉字（規格 §4.2 踩過）。

⚠️ **缺口門檻不改**（還是「連續 30 秒沒有資料」）：2026-09-07 量過他那份真的取樣檔，
相鄰兩列中位 457 ms、最大 1,628 ms、**秒與秒之間最大只跳 2 秒** ⇒ 30 秒離取樣自己的
抖動還有一個數量級，不會誤報。**改的是那句話**，因為取樣工具「有變才記」，
空白那一段有兩種可能，寫死「不是沒行情」是講了一句我們證不了的話。

⚠️ **`auto` 桶寬對取樣日的下限是 2 秒不是 1 秒**。用他 2026-09-07 那份真取樣檔
（2,972 列）實測：1 秒桶 1,504 個、平均 **1.98 個點**，其中 **26.7% 高＝低**
（401 個 —— 秒 K 退化成一根橫線，看起來像「這一秒沒動」）；
2 秒桶 755 個、平均 3.94 個點，高＝低降到 **0.9%**（7 個），
「這一段摸到多高多低」才畫得出來。
⛔ **只動 `auto`** —— 他手動按「1 秒」還是要給他 1 秒。
⚠️ **2026-09-07 更正**：這裡原本寫「一半的桶只有 1 個點」，那個數字**沒有量過**
（實測只有 1 個點的是 **13.3%**＝200/1504）。撐住這個決定的是高＝低那 **26.7%**。

⚠️ **同一件事的產品後果：取樣日的「高低」不是那一秒真正的高低。**
取樣列只有**一個** `price`，開高低收四個值全部來自那一個取樣點 —— 那四個數字沒有無中生有
（它們真的是那一秒**取樣到的**極值），但秒 K 之所以是預設圖種，理由正是
「K 棒多給的是這一段摸到多高多低」，而取樣日恰好就是那個東西不成立。
⇒ **金籤與副標都要把這句話講出來**（`高低＝取樣點的極值，不是那一秒真正的高低`）。

⚠️⚠️ **取樣檔可能含 09:30 之後的資料 ⇒ 後端一定要切窗口**（2026-09-07 加）。
`tick_recorder.py --until 13:45` 是它自己說明裡就有的用法；照收會給出 **8,000+ 個桶**，
**打破 §6.2 的「一天最多 2,700 個桶」不變式**（那是前端固定時間軸與效能的依據），
關掉「時間軸固定」之後整個早上會被壓成一小段。
所以 `_tick_load()` 與 `_tick_load_polled()` **兩條路都切** `[08:45:00, 09:30:00)`，
⛔ **被切掉幾列一定要有一個數字**（`outwin` → 副標寫「另有 N 列在 08:45~09:30 之外」）。
⛔ 不要只切取樣那一半 —— 不變式是**整頁**的性質，對某一種檔失效等於埋一顆看不見的地雷。

**`/api/tick/days` 不准解析整個檔。** 一年後這裡會有 240 個檔、每個 5MB，
每次列目錄都全解析 = 一分多鐘。它只准做：列目錄 ＋ 前 8KB 嗅探 ＋ `st_size` / `st_mtime`。
筆數、涵蓋時段、缺口這些**要真的切到那一天才由 `/api/tick/day` 給**。
⚠️ 因此 §6.1 清單裡的「128,431 筆」只有**已經載入過的那幾天**顯示得出來；
沒載入過的顯示日期＋星期即可（**不要顯示估算值** —— 這個專案不放沒把握的數字）。

### 6.3 換日的四道守衛（⛔ 即時分頁已經踩過，這裡點名要求避開）

1. **換日請求要帶流水號，只認最後一次的回應**。
   ```js
   const my = ++TK.seq;
   fetch(url).then(r=>r.json()).then(x=>{ if(my!==TK.seq) return; ... });
   ```
   連按 ◀ 時先送的請求可能後回來（每換一天後端就要重解析一個 5MB 的檔）。
   即時分頁 2026-08-23 實測過：舊那天的資料蓋回快取，而且日期剛好又對得上，
   「載入中」那道守衛判定不出來 ⇒ 畫面在「今天」底下顯示別天的圖。
2. **換日到新資料回來之間那一秒，不可以把舊資料掛在新日期底下**。
   `TK.date`（想看哪天）與 `TK.data.date`（手上這份是哪天）**必須是兩個欄位**，
   兩者不相等 ⇒ 圖畫骨架、副標寫「載入中…」、筆數與缺口整組藏起來。
   ⛔ 不可以只用一個 `TK.date` 兼兩份工作。
3. **沒有錄到的日子要選不到**：不在 `/api/tick/days` 回傳的清單裡 ⇒ ◀▶ 直接跳過、
   清單裡不出現。◀▶ 走的是**清單的索引**，不是「日期減一天」。
4. **日期鈕的寬度不准隨狀態變**。載入中只把日期轉灰（`.loading`），
   **不可以把日期換成「載入中…」** —— 那會讓按鈕瞬間變寬約 33px，
   靠右對齊的 ◀ 被推出滑鼠底下，連點時第 2 下會落在日期鈕上（即時分頁實測 4/5 生效）。

### 6.4 今天（還在長）與過去（已完成）行為不同

| | 今天 | 過去 |
|---|---|---|
| 抓資料 | 切進來抓一次，之後**每 2 秒抓增量** | 切進來抓一次，之後不再抓 |
| 停止輪詢的條件 | 分頁不在前景 ／ 使用者翻到別天 ／ 後端回 `complete:true` | — |
| 右緣 | 貼齊資料右緣時**自動跟著往前**；使用者拖走過就**停止跟隨** | 不跟隨 |
| 未到的時段 | 畫「還沒到」淡斜線 | 不畫（過去的日子沒有「還沒到」） |
| 副標 | 「錄製中 · 最後一筆 09:12:34」 | 「已完成 · 08:45:02~09:29:59」 |

- **輪詢節奏 2 秒**：`tick_writer` 是每 1.0 秒批次 flush，所以磁碟上的資料本來就有
  ≤1.5 秒延遲。用 1 秒去輪詢只會常常拿到 0 個新桶。
- **`complete` 由後端算**：`date < today` 或 `now > 09:31`。
  ⛔ 用後端的 `snapshot()["today"]`，**不可以用瀏覽器的 `new Date()`**
  （跨午夜兩邊會不同一天 —— 面板已經為這件事踩過一次）。
- **自動跟隨的判定**：`|視窗右緣 - 資料右緣| <= 2 秒` 才跟隨。
  使用者一旦拖曳或縮放，在畫面右上角顯示一顆「回到最新」的小鈕（`--gold` 外框），
  ⛔ **不可以直接把他拉回去** —— 他可能正在看某一段。

### 6.5 第一次打開一定看到的畫面，就是空狀態

上線當天 `tick_logs/` 裡合格的逐筆檔可能是 **0 個**（今天那個是輪詢檔，見 §6.2）。
所以空狀態不是邊角，是主流程，要做完整：

| 情境 | 畫面 |
|---|---|
| 一個逐筆檔都沒有 | 「還沒有逐筆紀錄。逐筆落地從 2026-09-08 開始，明天早上 08:45 一開盤就會自動錄。」＋一行細字說明檔案會落在哪 |
| 今天有檔、但現在 < 08:45 | 「今天還沒開始錄（08:45 開始）」＋一顆「看上一個有錄的日子 →」 |
| 今天 08:45~09:30、剛開盤還沒幾筆 | 正常畫圖（哪怕只有 30 秒），不要用空狀態擋掉 |
| 選到的那天檔案解析失敗 | 「這天的紀錄讀不出來（第 N 列壞掉）」＋照樣顯示翻頁列 |

⛔ **任何狀態下翻頁列都不准消失**（即時分頁 2026-08-25 修過同一個病）：
「換到有資料的那天」是所有壞狀態下唯一的自救路徑。

## 7. 資料怎麼進到前端（**這一節決定整個實作，照做**）

### 7.1 結論

**後端分桶，一天一次給 1 秒桶的 columnar 陣列；前端只做「像素分桶」與繪圖。**
⛔ **不要把 jsonl 整份丟給前端。**

實測（本機，合成 135,001 列 / 7.70 MB 的一天，等同 9 萬筆成交 ＋ 4.5 萬筆買賣價）：

| 做法 | 大小 | 後端成本 |
|---|---|---|
| 原始 jsonl 直接丟 | **7.70 MB** | 0（但前端要 parse 13.5 萬個物件） |
| 1 秒桶 · columnar · 純價格 | **146 KB**（gzip 23.5 KB） | 全檔解析＋分桶 **0.31~0.33 秒**（之後走快取＝0） |
| 1 秒桶 · 物件陣列 | 241 KB | 同上 |

**146 KB vs 7.70 MB ＝ 小 53 倍**，而且**上限固定**：一天最多 2,700 個 1 秒桶，
不管他那天成交 8 萬筆還是 20 萬筆。這一點比壓縮率更重要 —— 逐筆的量是會長的。

- **不做 gzip**：面板是 loopback，146 KB 的傳輸成本量不出來，
  多一個 `Content-Encoding` 分支就多一個會壞的地方。
- **不做整數 delta 編碼**：實測只從 146 KB 省到 61 KB，
  但要在兩端各寫一次編解碼 —— 那正是最容易寫錯又最難察覺的地方（單位差一半，圖照樣畫得出來）。
  **直接送價格數字**（`Math.round(p*10)/10`）。
- **一定要 columnar**（`{"o":[...],"h":[...]}`），不要物件陣列
  （`[{o,h,l,c},...]`）：欄名在 2,700 個物件裡重複 2,700 次。

### 7.2 為什麼 1 秒是原子單位（這是產品決定，不是效能妥協）

繪圖區 976px、45 分鐘 ⇒ **一個像素 2.77 秒**。
就算他放大到只看 1 分鐘，976px / 60 秒 ⇒ 一個像素 0.06 秒 —— **一根 1 秒 K 佔 16px**，
已經是他螢幕上能分辨的極限。再細的資訊沒有像素可以放。

1 秒桶保留 `開/高/低/收/量/該秒最低買價/該秒最高賣價`，
**「這一段摸到多高多低」完全沒有損失** —— 那正是 ±100 觸價規則唯一在意的東西。
真正丟掉的只有「同一秒之內誰先誰後」，那件事在任何縮放倍率下都畫不出來。

⛔ 所以**不做** `/api/tick/raw`（逐筆原始列）這個端點。多一條路就多一份 schema、
多一個「前端不小心要了 6MB」的可能。將來真的需要（例如要看某一秒內的成交順序），
再開一個**限定窗口 ≤ 60 秒**的端點，不要現在先做。

### 7.3 端點契約

```
GET /api/tick/days
→ {
    // kind：tick＝逐筆／polled＝取樣（2026-09-07 加）
    // alt ：同一天另一種檔也存在、但沒被採用（逐筆優先）
    "days":[ {"d":"2026-09-08","w":"一","empty":false,"kind":"tick","alt":false},
             {"d":"2026-09-05","w":"五","empty":false,"kind":"polled","alt":false} ],
    "since":"2026-09-08",       // 開始有紀錄的第一天（UI 用來講「更早以前沒有錄」）
    "skipped":["2026-09-07"]    // 嗅探判定內容跟檔名對不起來的檔（UI 不顯示，給除錯看）
  }
```

```
GET /api/tick/day?date=YYYY-MM-DD&from=<秒>
→ {
    "date":"2026-09-08",
    "v":1,                    // 檔頭的格式版本；多個檔頭取最後一個，不一致就回報
    "heads":2,                // 檔頭列數 ＝ 面板當天重啟了幾次
    "sec0":31500,             // 08:45:00 的當日秒數（固定；前端算 x 用）
    "s":[2,3,4,...],          // 每個桶的秒（相對 sec0），遞增，缺的秒就是沒有成交
    "o":[],"h":[],"l":[],"c":[],  // 該秒的開高低收（實際價格）
    "vq":[],                  // 該秒成交量加總
    "bl":[],"ah":[],          // 該秒的最低買價、最高賣價（沒有 bidask 的秒填 null）
    "gaps":[{"sec":1234,"n":128,"why":"queue_full"}],   // k:"x" 的痕跡
    "bad":0,                  // 解析失敗的列數（要顯示，不可以吞掉）
    "n":128431,               // 成交筆數（取樣日＝取樣列數）
    "first":"08:45:02.117","last":"09:29:59.870",
    "complete":true,
    // ── 2026-09-07 加（逐筆／取樣共用同一種格式，前端不必寫兩套）──────────
    "kind":"tick",            // tick / polled
    "has_vol":true,           // ⛔ 取樣日是 false：量柱那顆疊圖要 disabled ＋ 寫出原因
    "ms_med":null,            // 取樣的中位間隔（毫秒）；逐筆日是 null
    "nopx":0                  // 取樣當下面板剛好沒有報價的列數（⛔ 不可以安靜地少）
  }
```

- `from` 省略 ⇒ 給整天。
- `from=<秒>` ⇒ 只回 **`s >= from`** 的桶。**含 `from` 本身**（那個桶上次拿到時可能還沒收完）。
  前端合併規則：**同 `s` 覆蓋，其餘 append**。
  ⛔ 不可以無腦 `concat` —— 會出現兩根同一秒的 K 棒（而且圖上看不出來，只有量會變兩倍）。
- 過去的日子忽略 `from`（反正有快取，整天給比較單純）。

### 7.4 後端快取（照 `/api/bars` 的教訓做）

`/api/bars` 曾經因為沒快取而整支 0.5~0.85 秒，壓成 20 秒快取後變 0.04 秒。
這張圖如果每次切分頁都重解析一次 5MB 會更痛。

```python
TICK_CACHE = {}        # date -> {"mtime":..,"size":..,"off":..,"buckets":{sec:[o,h,l,c,v]},
                       #          "bl":{},"ah":{},"gaps":[],"n":..,"bad":..,"first":..,"last":..}
TICK_LOCK = threading.Lock()
```

- **快取鍵一定要帶檔案的 `mtime` ＋ `size`**（跟 `_SESS_BACK` 同一招）。
- **過去的日子**：`mtime`/`size` 沒變就直接用快取，**永久有效**（檔案不會再長）。
- **今天**：走**增量**。記住上次讀到的 byte 位移 `off`，`seek(off)` 只讀新增的那段，
  合併進既有的桶。一次輪詢只會有 ~100 列，成本趨近 0。
  - ⛔ **讀到最後一列如果不是以 `\n` 結尾，那一列丟掉、`off` 退回上一個換行處。**
    append 寫入不是原子的，一定會讀到半列。
  - 檔案變小了（不該發生，但看門狗＋磁碟異常時可能）⇒ `off` 歸零重讀整檔，不要硬接。
- **多列檔頭是正常的**（看門狗重啟就多一列 `k:"h"`）。解析時直接跳過，
  但要數出來放進 `heads`。
- ⛔ **`TICK_LOCK` 只保護這份快取，絕對不可以碰 `state_lock`**，
  也不可以在解析時持有任何 `on_tick` 路徑上的鎖。`ThreadingHTTPServer` 會讓兩個
  請求真的同時跑，0.3 秒的解析卡在 `state_lock` 上就是卡住整個面板的報價。
- 解析失敗的列**計數不丟棄地回報**（`bad`）。「安靜地少」是這個專案明令禁止的失敗模式。

### 7.5 前端持有的資料

```js
TK.data = { date, s:Int32Array, o:Float32Array, h,l,c, vq:Int32Array, bl,ah, gaps, meta }
```

- **用 TypedArray**，不要物件陣列。2,700 個桶 × 8 個 Float32 ≈ 86 KB，
  整天的資料留在記憶體裡完全無壓力（demo 實測：載入 40,000 點的合成資料，
  JS heap 從 9.54 MB 變 9.54 MB，差 0.00 MB —— TypedArray 的代價量不出來）。
- **每個日期一份，最多留 3 份**（今天 ＋ 前後翻的兩天），超過就丟最舊的。
  換日不要每次都重抓。

### 7.6 ⛔ 這一頁一行都不准碰 `on_tick`

想「從記憶體佇列直接拿最新的 tick，就不用等 flush」——**不可以**。
`on_tick` 跑在永豐 SDK 的回呼執行緒上，**它更新的價就是停損看的那個價**
（永豐沒有停損單，停損活在 Python 迴圈裡）。那條路上多一個讀鎖就是多一次可能塞住他的停損。

代價是**今天的最後一筆有 ≤1.5 秒的落地延遲**（`flush_every=1.0`）。
這是刻意的取捨，在 `.tk-foot` 直接寫出來：「落地延遲約 1 秒」。
⛔ 不要為了少那 1 秒去動 `tick_writer` 的 `flush_every` 或碰佇列。

## 8. 繪製實作要點（全部來自實測，不是偏好）

### 8.1 Canvas，不要 SVG

即時分頁的 K 線圖是 SVG（60 根，完全夠用）。**這張圖不可以照抄**。
2026-09-07 實測（headless Chrome，真滑鼠拖曳 60 步，量的是每一步的實際耗時）：

| 資料 | 圖種 | 畫法 | 單次繪製中位 | 拖曳每步 | fps |
|---|---|---|---|---|---|
| 40,000 點 | 折線+價帶 | **SVG path** | 50.8 ms | **155.1 ms** | **6.4** |
| 40,000 點 | 折線+價帶 | Canvas 全部點 | 7.4 ms | **152.8 ms** | **6.5** |
| 40,000 點 | 折線+價帶 | **Canvas 像素分桶** | 3.4 ms | **15.4 ms** | **65.1** |
| 40,000 點 | 秒K 5 秒 | Canvas | 0.7 ms | **6.95 ms** | **143.9** |
| 2,212 點 | 折線+價帶 | SVG path | 4.0 ms | 17.6 ms | 56.9 |
| 2,212 點 | 秒K 5 秒 | Canvas | 0.8 ms | 7.2 ms | 139.2 |

- SVG 在 40,000 點時 `d` 字串長 **973,543 字元**，每次拖曳都要重建整條字串再交給排版引擎。
- **SVG 與「Canvas 但不分桶」兩條路都淘汰**（拖曳 6.4 / 6.5 fps，手感是「黏住」）。
- DOM 節點數：SVG 版 158、Canvas 版 156 —— 差別不在節點數，在每格的重建成本。

### 8.2 像素分桶是必須，不是優化

```
一個像素欄只留 min / max / first / last（買賣價另留 bidMin / askMax）
畫：① 每欄的 min~max 一條 1px 垂直線（＝那一欄真正的振幅，不會被抽掉）
    ② 各欄的 last 連成折線
```

- 欄數 = `Math.ceil(PW)`。**一個像素欄本來就塞不下兩個以上的值**，
  所以這不叫「抽稀」——畫面上看到的東西**一模一樣**（§12 驗收 2 有逐欄比對的硬證明）。
- 實測 40,000 點在分桶後只畫 **1,336 個元素**，秒K 更只畫 **91 根**。
- ⛔ **不可以用「每 N 筆取一筆」的等距抽樣** —— 那會漏掉尖峰，
  而尖峰正是 ±100 觸價唯一在意的東西。

### 8.3 canvas 的 `width` / `height` 只有尺寸真的變才准動

```js
if (w===W && h===H && dpr===DPR && cv.width) return;   // 這一行不准拿掉
```

寫 `canvas.width`（就算寫同一個值）會重新配置整張後備緩衝區並清空。
**demo 實測：2,212 點時一次 draw 從 2 ms 變 129 ms（64 倍）。**
`fitCanvas()` 每次 draw 都會呼叫，所以這道守衛在熱路徑上。

### 8.4 其他

- **視窗內索引用二分搜**（資料本身時間遞增），不要每次 `filter` 整條陣列。
- **游標十字線不要重畫整張圖**：如果之後覺得 hover 卡，把十字線移到第二張疊在上面的
  `<canvas>`。**現在先不要做**（實測 hover 重畫整張是 7 ms，做分層是多一份同步負擔）。
- **滾輪縮放以游標為錨**、**拖曳平移**；縮放上限＝視窗 10 秒，下限＝完整 45 分鐘 ×1.2。
- **圖表容器只建一次，之後只換 canvas 內容**；整塊 innerHTML 重繪會打斷縮放/拖曳並閃爍。
- **每 2 秒重繪的東西一律不准掛 CSS animation**（面板鐵律）。
- 分鐘/秒的換算一律 `Math.floor` 不可以 `round`（demo 踩過：290 秒被印成「5 分 50 秒」）。

## 12. 驗收條款（dev 自測 ＋ lab-qa 照著量）

> 每一條都給了**量法**與**負控組**。沒有負控組的綠燈在這個專案不算數
> （「有測試」不等於「測試在保護那件事」）。
> 探針放 `tools/probe/tick-tab.mjs`，沿用 `cdp.mjs`；治具用合成資料，
> ⛔ **一個真實成交價、真實進出場時間、真實點數都不准進探針或治具**。

**1. 4 萬點的繪製與拖曳**
造一份 40,000 筆、鋪滿 08:45~09:30 的合成逐筆檔（價格用 12000 附近的假數列）。
用 CDP `Input.dispatchMouseEvent` 真的拖 60 步，量每一步的耗時（中位）：

| 組合 | 門檻 | 這份 demo 實測 |
|---|---|---|
| 秒K（自動桶寬） | 每步 ≤ 20 ms | 6.95 ms |
| 折線 + 價帶（像素分桶） | 每步 ≤ 30 ms | 15.37 ms |
| 單次繪製（25 次中位） | ≤ 12 ms | 3.4 ms |

**負控組（尺的自證）**：把 render 切成「不分桶」跑同一份資料，
每步**必須** ≥ 100 ms（demo 實測 152.8 ms）。如果負控組也很快，就是量錯了，這一條不算過。

**2. 抽稀之後看不到什麼（硬證明，不准用肉眼）**
在同一個視窗、同一份資料下，分別用「像素分桶」與「全部點」算出**每一個像素欄的 min/max**，
逐欄比對：**必須 100% 相等**（分桶保留每欄的最高最低，這是無損的）。
斷言 `maxColDiff === 0`。
差異只准出現在「同一像素欄內的先後順序」——**這一點要寫進探針的註解**，
下一個人才知道我們丟掉的是什麼。
**負控組**：把分桶改成「每 30 筆取一筆」，`maxColDiff` **必須 > 0**。

**3. 換日不會錯置**
① 用 CDP `Fetch.enable` 把「第一個 `/api/tick/day` 請求」延遲 800 ms、後續不延遲。

**4. 缺口有講出來**

**6. 舊的輪詢檔不可以被當成逐筆檔**
